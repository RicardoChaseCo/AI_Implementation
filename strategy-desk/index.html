策略评测台

发卡机构改一条通过策略，正式做法是在冻结的历史申请上重跑，和正在生产的冠军策略逐笔比差异，再由人签字。国内这套工具是这条链路的缩小版：一张客群格子表、一份整理过的小样本、一次模型第二遍检查，以及一份审计。

01业界的策略评测怎么走

生产决策引擎里，分析师改的不是「这个格子通过率写成 41%」。格子里放的是规则参数：分数线、负债率上限、额度上限、拒绝原因。通过率是拿一批已经发生过的申请重算出来的结果。

flowchart TD
  A[分析师修改决策表] --> B[参数: 分数线、额度、拒绝原因]
  B --> C[取申请当时已经知道的特征]
  C --> D[冠军策略和候选策略各跑一遍]
  D --> E[逐笔比较: 通过率、换入、换出]
  E --> F[第二人复核并留下审计]
  F --> G[生产上小流量挑战者]
  G --> H[等表现窗口看坏账]
  H --> I[再决定是否全量]

正式上线停在表现窗口之后。回放当天看不到换进来的人以后会不会逾期。

冠军 / 挑战者冠军是现在生产上的策略。挑战者是准备替换它的版本。回放阶段两套都只在历史数据上跑，客人无感知。
时点冻结重跑去年三月的一笔申请，只能用当时已经拿到的征信、收入和分数。之后的还款不能当成当时的输入。
换入 / 换出换入是冠军拒绝、候选通过。换出相反。通过率没变，也可能是换入一百人、换出一百人，人群已经不同。
表现窗口坏账通常要等六到十二个月。回放可以比较通过了谁，不能证明坏账下降。所以回放通过不等于可以全量。
第二双眼睛可以是另一位分析师，也可以是一个模型先把可疑格子标出来。模型不能代替签字。不利行动原因、最终通过还是拒绝，都以人确认的那一版策略为准。

02国内这套工具实际做了哪一段

美国有正式回放平台。国内分析师不能把策略贴进外面的聊天工具，也排不上反复跑全量。软件做的是一个本地评测台，用来在小样本上把一版改动看清楚，再交回正式流程。

环节发卡机构的正式平台你们的本地评测台
策略怎么表达决策表里的分数线、额度和原因码客群档位 × 格子。分析师直接改各档通过率或规则场景
数据全量申请日志，特征按申请时点冻结一份整理过的小样本，同样只使用申请时点已经知道的字段
比较按申请号逐笔算换入、换出几个版本并排跑，先汇总到客群格子的差异
复核人签字，变更单留痕模型按固定制度标出可疑格子，标记和文档清单入库，人决定改不改
上线小流量挑战者，再等表现窗口不做。本地台不发布到生产决策引擎
格子上的通过率差，不要讲成逐笔换入人数。只把通过率从 28% 改到 41%，说明这一档放松了；里面哪些人被换进来，要有申请号对齐才算得出来。那一步在正式回放里做。

04技术架构

一个内部 Web 服务就够了。格子、样本、版本、模型和审计都归它。没有再拆一排微服务，也没有把美国的决策引擎重写一遍。

flowchart LR
  subgraph desk [本地评测台]
    ui[格子页面]
    svc[评测服务]
    sample[(冻结样本)]
    ver[(策略版本)]
    audit[(审计日志)]
    ui --> svc
    svc --> sample
    svc --> ver
    svc --> audit
  end
  docs[按策略类型挂好的制度文档] --> svc
  svc --> llm[公司允许的模型接口]
  llm --> svc
  subgraph us [本地没有重建]
    engine[生产决策引擎]
    full[全量逐笔回放]
    live[线上挑战者]
  end
  audit -. 人确认后走正式变更 .-> engine

虚线不是自动发布。分析师接受或驳回标记之后，变更仍走原来的上线流程。

服务里有四张东西

  • 样本：申请号、客群、申请时点特征、冠军当时的结论。
  • 版本：谁在什么时候把哪一格从多少改到多少。
  • 结果：这一版各档人数和通过率，以及和冠军的差。
  • 审计：用了哪几份制度、送给模型的差异、模型原文、人的处置。

页面上分析师能做的事

  • 选一份已经冻结的样本，打开冠军版本。
  • 复制出候选，改客群格子。
  • 提交一个小任务。几个候选可以并排跑。
  • 读标记，留下「采纳 / 驳回」。

任务很小，所以分析师等在页面上就能看完。多个候选版本各跑各的，比的是同一份样本。样本里没有表现窗口时，结果区只谈通过率差异，不谈坏账改善。

正式回放还会按申请号做连接：同一笔申请在冠军和候选下各有一个通过或拒绝，才能数换入和换出。本地台如果只汇总到客群，面试里就说到格子差异为止，把逐笔对账留给美国那套平台。

06模型怎么评审，检索为什么停

没有微调。一次接口调用。系统提示里是评审规则：某一档相对冠军偏离过大，相邻客群通过率倒挂，改动和书面制度冲突，就标出来。上下文里放这次格子差异，以及这份策略对应的那几份制度。制度是按策略类型事先挂好的，不是临时从网上搜。

检索起过一条最小的路，没有进这条主路径。制度按章节切开，用同一家模型的向量接口做成向量，放在内网的小索引里。评审时用被改的格子和规则原文去查，打算把命中的几段拼进提示词。

主路径

  • 策略类型决定挂哪几份制度。
  • 差异和制度原文一起交给模型。
  • 同一版差异，下次还能复现同一份输入。
  • 标记入库，人处置。

检索停在主路径之外

  • 制度不长，人已经站在那个格子上，相关条款是确定的。
  • 检索经常把相邻产品的条款带进来，比指定文档更吵。
  • 索引一更新，同样的差异会检出不同段落，审计对不上。

所以面试里可以这样收：检索没有进主路径。正式评审按策略类型挂好固定制度，和格子差异一起交给模型，标记全部入库。

07三周到三天说的是哪段等待

时钟的起点是「这版策略改动提出来」，终点是「评测意见可以交回去」。三周里大头是等美国平台排期、等全量回放、再人工从头读。三天是分析师在本地样本上自己重算，并且先看被标出的格子。

不要把三天讲成全量回放变快了，也不要讲成模型批准了策略。样本不是全量生产流量。抓到的是规则配错，例如某一档一次抬得过高、相邻档倒挂。两个月里三十多条，指分析师确认过的这类配错。线上坏账好不好，本地台回答不了。

讲的时候按这个顺序

美国平台做全量逐笔回放和上线。我们做国内分析师能自己跑的缩小版。
页面是客群格子。小任务在冻结样本上重算各档，几个版本并排比。
模型是第二遍检查。制度按策略类型固定放进提示词。每条标记入库，人签字。
检索做过按章节切分和内网向量索引，因为复现和噪声停在主路径外。
原型里的 8,000 笔、通过率和分数线都是为了把流程讲清楚。制度没有使用真实文件名。生产决策、全量换入换出和挑战者实验不在这个本地台里。
